# Internationalization and localization

CGP provides English and Polish for all application-owned copy. This includes navigation, the tutorial and sample listings, tournaments, brackets, rankings, map veto, account and recovery forms, chat controls, moderation, empty states, errors, accessible names and account emails.

User-authored names, messages, listing descriptions, availability and administrator announcements remain unchanged. They are content, not translation keys. A language change must never replace a username, alter a draft, or translate a private message.

## Language and region selection

The header's language and region control offers automatic selection and explicit choices. Country names come from `Intl.DisplayNames`. Language options use their native names and language attributes.

1. A saved explicit language takes precedence.
2. For a visitor without a saved choice, valid `lang` and `region` parameters in an account email link provide defaults.
3. Otherwise, the first valid device locale supplies the region. Language-only device tags use `Intl.Locale.maximize()` to infer their usual region.
4. Automatic language is Polish for region `PL` and English for every other region. The fallback region is `GB`.

An explicit region overrides the device region. Language and region are stored separately as `cgp-language` and `cgp-region`. Returning the language to Automatic makes it follow the selected region again. Changes also synchronize between tabs. Storage failures leave selection available for the current page.

Region detection uses browser preferences, not physical location. An English-US browser in Poland therefore initially receives English until its region or language is changed. There is no location permission request, external geolocation service or IP lookup.

## Source files and messages

| File | Responsibility |
| --- | --- |
| `frontend/locales/en.js` and `pl.js` | Shared, matching catalogs consumed directly by the browser and Node. |
| `frontend/i18n-core.js` | Language resolution, English fallback, interpolation, plural selection and formatting. |
| `frontend/i18n.js` | Browser preferences, translated DOM bindings and live updates. |
| `backend/i18n.js` | Request language negotiation and message envelopes. |
| `frontend/accessibility.js` | Dialog focus containment, Escape handling and focus restoration. |

Keep semantic keys stable. For new copy, add both translations and use a complete sentence with named placeholders. Avoid composing sentences from translated fragments or placing language-dependent labels in application state. Use stable values such as `entry`, `open`, `win` and `loss` for filtering, routing and calculations.

Use `data-i18n` for plain text and `data-i18n-attr` for attributes. Attribute bindings may contain semicolon-separated pairs, for example `aria-label:chat.title;title:chat.title`. Bindings accept JSON parameters through `data-i18n-params`. Do not attach a text binding to an element containing an input or other state that must survive translation.

For dynamically created DOM, `CGP_I18N.bind(element, key, values)` records a live text binding. `CGP_I18N.fragment(key, values)` produces a live translated fragment for HTML templates. Rich messages permit only catalog-owned `b`, `strong`, `em` and `code` tags without attributes. Parameters are escaped. Do not pass prebuilt HTML as a translation parameter or insert unescaped user content.

`CGP_I18N.t(key, values)` returns plain text. Missing Polish keys fall back to English; missing English keys display their key and fail reference coverage checks. Plural entries use `Intl.PluralRules`: include `one` and `other` for English, and `one`, `few`, `many` and `other` for Polish.

To add a language, register its tag in `i18n-core.js`, add a matching catalog and selector option, load it before the runtime, register it on the backend, and extend parity and behavioral tests. Review automatic regional defaults explicitly.

## Regional formatting and API behavior

Formatting uses a BCP 47 language-region tag, such as `en-US`, `en-PL` or `pl-PL`, with native `Intl` date, number, currency, relative-time and list formatters. Browser locale data controls the closest supported format for each combination. Dates and times use the viewer's device time zone. Selecting a region does not change the time zone or convert currencies.

Tournament `start` and match `time` fields contain ISO 8601 timestamps or `null`. Maps without an assigned value are `null`. The API no longer sends Polish display dates or placeholder labels. Keep dates as timestamps through sorting and storage; format them only when displaying them.

The browser sends `X-CGP-Language` and `X-CGP-Region` on API requests. API consumers without these headers use `Accept-Language` regional preferences with quality weighting. A failure includes `error`, `errorKey` and `values`; an application success message includes `message`, `messageKey` and `values`. Data messages such as a stored chat message remain data objects.

The selected language also applies to registration, activation resend and password recovery mail. Activation/reset links preserve language and region defaults on another device. Email HTML declares its language and escapes personalized content. No account preference column or database migration is required.

Frontend code, styles and catalogs revalidate on page loads. Release asset URLs bypass caches from the earlier partial implementation. Deploy frontend and backend together because of the timestamp and message-envelope changes.

## Accessibility scope

The document language and title update with the interface. Language options identify their own language. Accessible labels, field labels, validation and status messages share the catalogs. The page includes a skip link, visible focus indicators, inert closed mobile navigation, and focus containment/restoration for account, chat and admin dialogs. Language changes preserve drafts and current tournament/veto state. Reduced-motion preferences disable the video and scramble behavior and remove animation delays.

These changes support the [WCAG language-of-page requirement](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html) and improve keyboard and screen-reader behavior. They do not establish WCAG conformance. A complete accessibility assessment, including assistive-technology testing, contrast, moving content, zoom/reflow and all interactive states, remains separate work.

## Validation

Run `npm test --prefix backend` on Node.js 22 or newer. Tests cover catalog parity and references, untranslated page text, interpolation safety, plural rules, language/region resolution, live bindings, storage failures, localized API validation/rate limits, ISO tournament data, email language and account links. Existing session, polling, moderation and request-limit tests remain required.

For browser checks, include English and Polish at desktop and mobile widths, signed-out/player/captain/admin states, all admin views, keyboard focus and Escape behavior, locale persistence, open form/chat/report drafts, veto progress, and explicitly identified demonstration behavior. Local API fixtures verify interface behavior only; they do not prove database persistence or real email delivery.
